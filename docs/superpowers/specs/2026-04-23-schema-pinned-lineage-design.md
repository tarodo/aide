# Schema-Pinned Lineage & Field Lifecycle — Design

**Date:** 2026-04-23
**Status:** Draft (awaiting review)
**Scope:** Phase 3 of dataset lineage. Pin `DatasetLink` to concrete `DatasetSchema` versions so AIDE becomes a data contract. Replace `Field.is_tech: bool` with a three-state `Field.origin` enum (`mapped` / `tech` / `deprecated`). Add an on-demand compatibility endpoint that ETL pre-flight uses to block loads on broken contracts.

**Related ADRs:** ADR-016 (two-level lineage, Phase 1 foundation), ADR-017 (tech-field templates, Phase 2), ADR-010 (enum-as-varchar), ADR-006 (soft-delete), ADR-014 (filter/sort contract).

---

## 1. Context and Problem

Phase 1 landed two-level lineage: `dataset_link(source_dataset, target_dataset)` with child `field_link(source_field, target_field)`. It answers **"what feeds what"** at identity level but has no notion of **which version of a schema** feeds which, and no notion of **lifecycle** for target fields that lose their source.

Two product pressures drive this phase:

1. **Data contract.** AIDE should be the source of truth that ETL jobs consult before loading: "is the source schema still compatible with what the target expects?" Today nothing in the model expresses this pairing — `dataset_link` is identity-level, and type information lives on `field_binding` (per-schema-version), which the link cannot see.
2. **Schema evolution without breakage.** When a source column is removed, downstream consumers of the target table still expect the column to exist. Today the model forces DDL drop on the target (violating the `is_tech=False → must have source` invariant) or reclassification as `is_tech=True` (which conflates "generated by pipeline" with "kept for backward compatibility"). Neither is right.

The design must:

1. Let a `dataset_link` pin to specific `dataset_schema` versions on both sides, so type compatibility is a well-defined join.
2. Detect **drift** (pinned version is not the latest) separately from **breakage** (types no longer compatible against the pin).
3. Classify target fields into three lifecycle states so that NULL-padded legacy columns are legal without abusing `is_tech`.
4. Expose the compatibility as a cheap, on-demand endpoint — no persisted snapshots in this phase.
5. Keep `field_link` at identity level (logical edge survives re-pin), not binding level (which would force re-creating links on every version bump).

## 2. Goals / Non-Goals

**Goals:**

- Persist `DatasetLink.source_schema_id` and `DatasetLink.target_schema_id` as NOT NULL FK to `dataset_schemas.id`, with `ON DELETE RESTRICT`.
- Introduce `FieldOrigin` enum on `Field` (`mapped`, `tech`, `deprecated`), replacing `is_tech: bool`.
- Add a compatibility algorithm that, for a given `dataset_link`, returns per-`field_link` issues (`source_unbound`, `target_unbound`, `type_incompatible`, `type_unsafe_cast`, `type_needs_cast`, `nullability_warn`) plus pin-drift flags.
- Expose two new endpoints: `GET /dataset-links/{id}/compat` (detailed per-link report) and `GET /dataset-links/compat` (bulk list for monitoring).
- Expose four new error codes covering schema/dataset mismatch, origin-transition conflicts, FieldLink/binding misalignment, and in-use schema delete attempts.
- Migrate existing `field.is_tech` to `field.origin` and existing `dataset_link` rows to pinned latest schemas without data loss.
- Keep the full four-package chain (`aide-schemas`, `backend`, `aide-sdk`, `aide-crawler`) coherent via a lockstep major bump.

**Non-Goals (deferred):**

- **Auto-propagation** of source type changes into target schemas via `CastRule` — ETL-side auto-remediation. Phase 4.
- **Webhook / push alerts** on drift. Phase 4.
- **Historical compat snapshots** / event log ("when did this link last pass?"). Phase 5+.
- **UI visualization** of compat graph. Separate frontend track.
- **Binding-level `FieldLink`** (i.e. link directly references `field_binding` rows). Considered and rejected — see §3.3 trade-offs.
- **Gradual / dual-support API migration** (accepting both `is_tech` and `origin` during a transition window). Internal monorepo — lockstep major bump is simpler.

## 3. Data Model

### 3.1 `DatasetLink` — pin columns

Two new columns on `dataset_links`:

```python
class DatasetLink(Base, SoftDeleteMetaDataMixin):
    __tablename__ = "dataset_links"

    # ... existing columns ...

    source_schema_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True),
        ForeignKey("dataset_schemas.id", ondelete="RESTRICT"),
        nullable=False,
        index=True,
    )
    target_schema_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True),
        ForeignKey("dataset_schemas.id", ondelete="RESTRICT"),
        nullable=False,
        index=True,
    )

    source_schema = relationship("DatasetSchema", foreign_keys=[source_schema_id])
    target_schema = relationship("DatasetSchema", foreign_keys=[target_schema_id])
```

**DB-level invariants** (existing from Phase 1 retained):

- `uq_dataset_link_pair_active` — partial unique on `(source_dataset_id, target_dataset_id)` where `deleted_at IS NULL`.
- `ck_dataset_link_no_self` — `source_dataset_id <> target_dataset_id`.

**Service-level invariants** (enforced in `DatasetLinkService`, not DDL):

- `source_schema.dataset_id == source_dataset_id`
- `target_schema.dataset_id == target_dataset_id`
- Both checked on `create` and on `update` (when `source_schema_id` or `target_schema_id` changes).
- Changing `source_dataset_id` or `target_dataset_id` on an existing link is rejected (immutable dataset identity). Delete + recreate is the supported flow.

### 3.2 `Field.origin` — lifecycle enum

Replace `Field.is_tech: bool` with:

```python
class FieldOrigin(str, enum.Enum):
    MAPPED = "mapped"          # must have inbound FieldLink as target
    TECH = "tech"              # generated by pipeline (CDC op, timestamps, hashes)
    DEPRECATED = "deprecated"  # no source, NULL-padded for backward compatibility


class Field(Base, MetaDataMixin):
    # ... existing columns ...

    origin: Mapped[str] = mapped_column(
        String(20), nullable=False, server_default="mapped"
    )
    # is_tech: bool REMOVED
```

**Invariants:**

- `origin == MAPPED` requires ≥1 active `FieldLink` row with `target_field_id = this.id` (was the Phase 1 invariant "non-tech target must have source").
- `origin == TECH` or `origin == DEPRECATED` requires **zero** `FieldLink` rows with `target_field_id = this.id` (target unlinked — it is generated or NULL-padded).
- Source-side origin is not constrained. A source field of any origin can feed a target. Usual case is `MAPPED`; a `TECH` source (e.g. CDC op at the source layer) can be forwarded too.

### 3.3 Why `FieldLink` stays at identity level (rationale)

Two alternatives considered:

- **Identity-level (chosen):** `FieldLink(source_field_id, target_field_id, dataset_link_id)`. Compat resolves `field_binding` via `dataset_link.source_schema_id` / `target_schema_id` at query time.
- **Binding-level (rejected):** `FieldLink(source_field_binding_id, target_field_binding_id, dataset_link_id)`. Types directly readable on the link row.

Trade-off:

| Axis | Identity | Binding |
|---|---|---|
| One logical edge across N schema versions | 1 row | N rows |
| Re-pin of parent `DatasetLink` | No-op for FieldLink | All FieldLinks must be re-created |
| Compat query | 2 extra JOINs on `field_binding` | Direct read |
| Invariant FieldBinding.schema_id == DatasetLink.(source\|target)\_schema_id | Enforced at compat time | Service-enforced on every write |
| "Unbound" after re-pin | Natural — compat reports it | Impossible — FK fails |

Identity-level is chosen because (1) the parent `DatasetLink` already pins versions — doubling the pin on `FieldLink` is redundant; (2) a logical edge survives re-pin, which matches the mental model "`price → price` has been the same contract across three source schema versions"; (3) the compat query's extra JOIN is cheap (`field_binding(field_id, dataset_schema_id)` is covered by the existing unique index).

Binding-level would be worth re-examining if field renames changed `Field` identity (they don't — rename is an `UPDATE` on the existing row).

### 3.4 Related tables — unchanged

`DatasetSchema`, `FieldBinding`, `FieldLink`, `Dataset`, `TypeInstance`, `DataType`, `CastRule`: **no schema changes**. Their existing shape is already sufficient. The compat algorithm reads from them.

## 4. Lifecycle and State Transitions

### 4.1 `DatasetLink` lifecycle

| Event | Rule | Error code on violation |
|---|---|---|
| `create` | Both `source_schema_id` and `target_schema_id` required. Each `schema.dataset_id` must equal the corresponding `dataset_id` on the link. | `SCHEMA_DATASET_MISMATCH` (422) |
| `update` | May change `source_schema_id` / `target_schema_id` (re-pin). Same belong-check. `DatasetLinkUpdate` schema **omits** `source_dataset_id` / `target_dataset_id` entirely — Pydantic rejects them with 422 if sent (no dedicated error code needed). | `SCHEMA_DATASET_MISMATCH` (422) |
| Post-re-pin FieldLinks | **Not auto-reconciled.** Existing `FieldLink` rows survive; compat report surfaces any that became `source_unbound` / `target_unbound`. Operator cleans up explicitly. | — |
| `soft_delete` | Unchanged from Phase 1 (sets `deleted_at`, releases partial unique). | — |

**Rationale for no auto-reconciliation on re-pin:** making re-pin a destructive operation (auto-deleting FieldLinks that became unbound) removes the operator's ability to diagnose why the link broke. The compat report is the diagnostic; the operator acts on it.

### 4.2 `FieldLink` lifecycle

| Event | Rule | Error code |
|---|---|---|
| `create` | `source_field` must have a `FieldBinding` in `dataset_link.source_schema_id`. `target_field` must have a `FieldBinding` in `dataset_link.target_schema_id`. `target_field.origin` must be `MAPPED`. | `FIELD_BINDING_MISSING` (422), `FIELD_ORIGIN_CONFLICT` (409) |
| post-re-pin existence | Lax: a `FieldLink` can survive its parent's re-pin even if the referenced field has no binding in the new pinned schema. Compat reports it as unbound; operator deletes it. | — |
| `delete` | Unchanged from Phase 1 (hard-delete, CASCADE via FKs). | — |

### 4.3 `Field.origin` state machine

Service `FieldService.update` enforces. All transitions are atomic in a single UoW with associated FieldLink operations.

```
        MAPPED ───────→ TECH            requires: zero active FieldLink with target_field_id = this.id
        MAPPED ───────→ DEPRECATED      requires: zero active FieldLink with target_field_id = this.id
        TECH   ───────→ MAPPED          requires: ≥1 FieldLink created in the same UoW with this as target
        TECH   ───────→ DEPRECATED      unconditional (both origins are "no source required")
        DEPRECATED ───→ MAPPED          requires: ≥1 FieldLink created in the same UoW with this as target
        DEPRECATED ───→ TECH            unconditional
```

On a blocked transition, the service returns `409 FIELD_ORIGIN_CONFLICT` with `blocking_field_link_ids: [uuid, ...]` (if transition is out of `MAPPED`) or `missing_field_links: true` (if transition is into `MAPPED` without accompanying FieldLinks).

### 4.4 `DatasetSchema` delete

`ON DELETE RESTRICT` on both `DatasetLink.source_schema_id` and `DatasetLink.target_schema_id`. PostgreSQL rejects the delete if any `dataset_link` row (including soft-deleted ones, since RESTRICT ignores `deleted_at`) references the schema.

The service catches the constraint error and returns `409 DATASET_SCHEMA_IN_USE` with `blocking_dataset_link_ids`. Operator re-pins or soft-deletes the blocking links first.

### 4.5 `Dataset` delete

Unchanged from ADR-016: service-level check blocks delete when any active `dataset_link` references the dataset as source or target. Schema pinning does not alter this path.

### 4.6 New `DatasetSchema` version registered (by crawler or manual API)

**No automatic action on any `DatasetLink`.** Pins continue to point at the previous version. Drift is detected at compat-query time (§5.2).

## 5. Compatibility Algorithm

### 5.1 `FieldCompatIssue` — per-field-link issue set

```python
class FieldCompatIssue(str, enum.Enum):
    SOURCE_UNBOUND     = "source_unbound"       # source field has no binding in pinned source schema
    TARGET_UNBOUND     = "target_unbound"       # target field has no binding in pinned target schema
    TYPE_INCOMPATIBLE  = "type_incompatible"    # types differ, no CastRule exists
    TYPE_UNSAFE_CAST   = "type_unsafe_cast"     # CastRule.safety == "unsafe"
    TYPE_NEEDS_CAST    = "type_needs_cast"      # CastRule.safety == "safe"
    NULLABILITY_WARN   = "nullability_warn"     # source nullable, target NOT NULL
```

A `FieldLink` may accumulate multiple issues (for instance `TYPE_NEEDS_CAST` and `NULLABILITY_WARN` together). An empty list means full compatibility.

**Severity mapping:**

| Severity | Issues | Recommended ETL behaviour |
|---|---|---|
| `error` | `SOURCE_UNBOUND`, `TARGET_UNBOUND`, `TYPE_INCOMPATIBLE`, `TYPE_UNSAFE_CAST` | Block load |
| `warn` | `TYPE_NEEDS_CAST`, `NULLABILITY_WARN` | Log, proceed (strict mode may block) |
| `ok` | Empty list | Proceed |

Severity of a `FieldLink` = max severity of its issues.

### 5.2 Algorithm (per `FieldLink`)

Inputs: `field_link`, `dataset_link.source_schema_id`, `dataset_link.target_schema_id`.

```
1. If field_link.target_field.origin != MAPPED:
       # Invariant violation — FieldLink should not exist. Defensive skip.
       issues = []; return.

2. source_binding = FieldBinding WHERE field_id = field_link.source_field_id
                                   AND dataset_schema_id = source_schema_id
   If source_binding IS NULL:
       issues.append(SOURCE_UNBOUND); return (do not probe types).

3. target_binding = FieldBinding WHERE field_id = field_link.target_field_id
                                   AND dataset_schema_id = target_schema_id
   If target_binding IS NULL:
       issues.append(TARGET_UNBOUND); return.

4. Type check:
   If source_binding.type_instance_id == target_binding.type_instance_id:
       skip type issue.   # exact TypeInstance reuse
   Else:
       source_dt = source_binding.type_instance.data_type_id
       target_dt = target_binding.type_instance.data_type_id
       rule = CastRule WHERE source_data_type_id = source_dt AND target_data_type_id = target_dt
       If rule IS NULL:
           issues.append(TYPE_INCOMPATIBLE)
       Elif rule.safety == "implicit":
           skip type issue.
       Elif rule.safety == "safe":
           issues.append(TYPE_NEEDS_CAST)
       Elif rule.safety == "unsafe":
           issues.append(TYPE_UNSAFE_CAST)

5. Nullability:
   If source_binding.is_nullable AND NOT target_binding.is_nullable:
       issues.append(NULLABILITY_WARN)
```

**Design notes:**

- Step 1 is defensive — the state-machine invariant (§4.3) forbids `FieldLink` where `target_field.origin != MAPPED`. If one is observed in practice, compat quietly returns empty issues; a separate integrity audit should surface it.
- Step 4 compares by `type_instance_id` equality first (fast path for reuse). `type_instance_id` equality implies same `data_type_id` and same `type_params`, so there is no "same data type, different params" edge case to handle separately — such cases naturally fall through to the `CastRule` lookup. Param-level semantics (e.g. `varchar(50) → varchar(100)` as implicit) live in a self-pair `CastRule` row seeded per flavor.
- Step 5 only flags the tightening direction. `NOT NULL → nullable` is a safe relaxation and not reported.

### 5.3 Link-level aggregation (response shape)

```json
{
  "dataset_link_id": "9f...",
  "pin_drift": {
    "source": { "pinned_version": 3, "latest_version": 4, "has_drift": true },
    "target": { "pinned_version": 1, "latest_version": 1, "has_drift": false }
  },
  "field_compat": [
    {
      "field_link_id": "8a...",
      "source_field": { "id": "...", "name": "price" },
      "target_field": { "id": "...", "name": "price" },
      "source_type": "numeric(10,2)",
      "target_type": "decimal(18,4)",
      "issues": ["type_needs_cast"],
      "severity": "warn",
      "cast_rule_id": "c2..."
    }
  ],
  "summary": { "ok": 12, "warn": 2, "error": 1, "total": 15 },
  "status": "error"
}
```

`source_type` / `target_type` are human-readable string renderings (e.g. `numeric(10,2)`) derived from the resolved `TypeInstance`. They are `null` when the corresponding side is unbound. `cast_rule_id` is populated only when a `CastRule` was consulted (steps 4's non-exact-match branch).

### 5.4 Link-level `status` rule

| Condition | `status` |
|---|---|
| Any `field_compat[*].severity == "error"` | `"error"` |
| No `error` but some `warn` **or** `pin_drift.source.has_drift` **or** `pin_drift.target.has_drift` | `"warn"` |
| No issues and no drift | `"ok"` |

Pin drift alone is `"warn"` — the contract is outdated but not broken against its current pin. ETL consumers decide whether to block on drift-only.

### 5.5 Why compat is not persisted

Three grounds for on-demand computation:

1. **Freshness.** Source of truth is `FieldBinding`, `CastRule`, `Field.origin`. Any persisted snapshot would be stale immediately upon a write anywhere in this chain.
2. **Cost is low.** Per link with N `FieldLink` children, compat resolves in roughly 4 JOINed queries: the link itself, `MAX(version_num) GROUP BY dataset_id` across two datasets, a single row-set SELECT over `field_link LEFT JOIN field_binding (src) LEFT JOIN field_binding (tgt) LEFT JOIN type_instance LEFT JOIN data_type LEFT JOIN cast_rule`. For links with 200 columns this is a single-digit millisecond query.
3. **Access pattern is bursty-read.** ETL pre-flight runs it once per dataset per load cycle; monitoring polls on a schedule. Neither justifies the complexity of a persisted, invalidated cache.

A persisted event log ("when did this link transition from OK to error?") becomes valuable only when we need historical audit. Out of scope.

## 6. API

### 6.1 Endpoints

| Method | Path | Status | Description |
|---|---|---|---|
| `POST` | `/dataset-links` | modified | Body requires `source_schema_id` and `target_schema_id`. |
| `GET` | `/dataset-links/{id}` | modified | Response includes `source_schema_id`, `target_schema_id`, plus nested summary of each pinned schema's `version_num`. |
| `PATCH` | `/dataset-links/{id}` | modified | Accepts `source_schema_id` / `target_schema_id`. Rejects attempts to change `source_dataset_id` / `target_dataset_id`. |
| `GET` | `/dataset-links/{id}/compat` | **new** | Full compat report per §5.3. 404 if link missing or soft-deleted; 200 otherwise (even if `status == "error"`). |
| `GET` | `/dataset-links/compat` | **new** | Bulk paginated list of compat summaries. Filters: `status` (repeatable), `has_drift`, `dataset_id`, `system_id`. Uses ADR-014 filter/sort dependency. |
| `PATCH` | `/fields/{id}` | modified | Accepts `origin`. Applies §4.3 state machine. |
| `GET` | `/fields` | modified | Filter `origin=mapped|tech|deprecated` (repeatable). |
| `DELETE` | `/dataset-schemas/{id}` | modified | Returns `409 DATASET_SCHEMA_IN_USE` with `blocking_dataset_link_ids` when referenced by an active `dataset_link`. |

### 6.2 `GET /dataset-links/compat` — bulk list item shape

```json
{
  "items": [
    {
      "dataset_link_id": "...",
      "source_dataset": { "id": "...", "object_name": "orders" },
      "target_dataset": { "id": "...", "object_name": "raw_orders" },
      "status": "error",
      "summary": { "ok": 12, "warn": 0, "error": 3, "total": 15 },
      "pin_drift": { "source": true, "target": false }
    }
  ],
  "total": 42,
  "page": 1,
  "page_size": 20

```

Sortable set for MVP: `{"status", "updated_at"}`. Sort by nested fields (`summary.error`, `source_dataset.object_name`) is out of scope — clients sort client-side from the page or add filters.

### 6.3 New error codes

| Code | HTTP | Trigger |
|---|---|---|
| `SCHEMA_DATASET_MISMATCH` | 422 | `schema_id.dataset_id != dataset_id` on the link side |
| `FIELD_ORIGIN_CONFLICT` | 409 | `origin` transition blocks the state machine |
| `FIELD_BINDING_MISSING` | 422 | `FieldLink` create — field has no `FieldBinding` in the pinned schema |
| `DATASET_SCHEMA_IN_USE` | 409 | `DELETE dataset_schemas/{id}` violates RESTRICT |

Registered in `backend/core/errors.py` (existing code registry per ADR-005).

### 6.4 ETL integration pattern (documentation, not endpoint)

Target doc: `docs/integrations/etl-pre-flight.md`.

Flow:

1. ETL worker knows `dataset_link_id` (from config or lookup by source+target names).
2. `GET /dataset-links/{id}/compat`.
3. Switch on `response.status`:
   - `"error"` → abort, alert owners.
   - `"warn"` → log all issues, proceed (strict mode in worker config may abort).
   - `"ok"` → proceed.
4. If `response.pin_drift.source.has_drift` or `target.has_drift` → emit informational notification for schema owners.

Webhook / push alerts for drift are out of scope (Phase 4).

## 7. Migration

### 7.1 Alembic migrations (two steps)

**Migration A — additive, nullable:**

```python
def upgrade():
    op.add_column("dataset_links",
        sa.Column("source_schema_id", UUID(as_uuid=True),
                  sa.ForeignKey("dataset_schemas.id", ondelete="RESTRICT"),
                  nullable=True))
    op.add_column("dataset_links",
        sa.Column("target_schema_id", UUID(as_uuid=True),
                  sa.ForeignKey("dataset_schemas.id", ondelete="RESTRICT"),
                  nullable=True))
    op.create_index("idx_dataset_links_source_schema",
                    "dataset_links", ["source_schema_id"])
    op.create_index("idx_dataset_links_target_schema",
                    "dataset_links", ["target_schema_id"])

    op.add_column("fields",
        sa.Column("origin", sa.String(20),
                  nullable=True,
                  server_default="mapped"))
    # is_tech remains for this step.
    # origin has server_default so new rows inserted between Migration A
    # and Migration B (by old or new app code) are never NULL.
```

**Backfill script `backend/scripts/migrate_lineage_pins.py`:**

```python
# Pseudocode. Real script uses async session and lives under backend/scripts/.

unresolved: list[tuple[UUID, UUID | None, UUID | None]] = []

# Idempotency: only touch rows that still have NULL pins.
# Re-running the script after fixing unresolved cases works correctly.
unpinned_links = select(DatasetLink).where(
    DatasetLink.deleted_at.is_(None),
    or_(
        DatasetLink.source_schema_id.is_(None),
        DatasetLink.target_schema_id.is_(None),
    ),
)

for link in session.scalars(unpinned_links):
    src_max = latest_schema(session, link.source_dataset_id)
    tgt_max = latest_schema(session, link.target_dataset_id)
    if src_max is None or tgt_max is None:
        unresolved.append((link.id, src_max, tgt_max))
        continue
    link.source_schema_id = src_max.id
    link.target_schema_id = tgt_max.id

# Field.origin: server_default from Migration A already wrote "mapped"
# for new rows. Backfill only rows that still carry the legacy is_tech=True
# signal. Idempotent: second run sees origin already == "tech" and no-ops.
session.execute(
    update(Field)
    .where(Field.is_tech.is_(True), Field.origin == "mapped")
    .values(origin="tech")
)
session.commit()

if unresolved:
    print("UNRESOLVED LINKS (links whose source or target dataset has no DatasetSchema):")
    for row in unresolved:
        print("  ", row)
    sys.exit(1)
```

Exit non-zero on unresolved forces the operator to create schemas (or soft-delete the orphaned link) before running Migration B.

**Migration B — finalize:**

```python
def upgrade():
    op.alter_column("dataset_links", "source_schema_id", nullable=False)
    op.alter_column("dataset_links", "target_schema_id", nullable=False)
    op.alter_column("fields", "origin", nullable=False, server_default="mapped")
    op.drop_column("fields", "is_tech")
```

### 7.2 Deploy sequence

Assumes a workflow where PR merge produces a build artifact but does not automatically deploy to prod — a human triggers deploy after migrations are applied.

| Step | Action | Reversible? |
|---|---|---|
| 1 | Merge PR with new model + service + API + SDK + crawler changes. Artifact built; **prod still running the old app.** | Yes (revert commit, rebuild). |
| 2 | Run Migration A on prod DB. New nullable columns appear; old app keeps working (it does not write to them). | Yes (Alembic downgrade drops the nullable columns). |
| 3 | Run backfill script. Fix any unresolved links manually (create a DatasetSchema for each dataset with none, or soft-delete orphan links), then re-run. Script is idempotent (§7.1 filters). | Idempotent — safe to re-run. |
| 4 | Deploy the new application binary to prod. New writes populate `source_schema_id` / `target_schema_id` / `origin` via ORM. | Rolling back to old binary is safe — new nullable columns are tolerated as long as Migration B has not run. |
| 5 | Soak period (hours to a day) to catch production surprises. Monitor error rates on the new endpoints. | — |
| 6 | Run Migration B. Columns become NOT NULL; `is_tech` dropped. | See §7.3 for caveats. |

### 7.3 Rollback risks

- **Migration A rollback** — clean drop of nullable columns. Safe.
- **Migration B rollback** — downgrade recreates `is_tech: bool`. Mapping: `is_tech = (origin == "tech")`. **`DEPRECATED` fields lose their semantic** on downgrade — they map to `is_tech=False` (mapped), which violates the Phase 1 invariant that mapped targets must have a source (they won't, by definition of being deprecated). Downgrade of Migration B is therefore safe **only** if no `DEPRECATED` fields exist in the database at downgrade time. Document this on the migration file header.
- **Application rollback after Migration B** — old code reads `fields.is_tech`, which no longer exists. Not supported. Revert the app and migration together.

## 8. ADR

New: **ADR-018 — Schema-pinned lineage and field lifecycle enum**. References ADR-016 as its predecessor. Captures the three key decisions that stand out:

1. **Pins on `DatasetLink`, not on `FieldLink`.** `FieldLink` stays identity-level so the logical edge survives schema evolution.
2. **`FieldOrigin` as a three-state enum**, not two booleans. Avoids the illegal `is_tech AND is_deprecated` combination and gives a single lifecycle axis.
3. **Strict `FieldLink` create, lax post-re-pin.** Create rejects dangling references; post-re-pin the compat report, not a constraint, surfaces newly-unbound fields.

Update `docs/adr/README.md` index table in the same commit.

## 9. CLAUDE.md Quirk Additions

Add under "Known quirks":

- After re-pin of `DatasetLink`, the compat report may show `source_unbound` / `target_unbound` for `FieldLink` rows whose fields have no binding in the new pinned schemas. This is expected — operator deletes them as part of the pin transition. It is not a constraint violation.
- `Field.origin` transitions are atomic with `FieldLink` create/delete operations in a single UoW. Sending `PATCH /fields/{id}` with `origin: "deprecated"` while the field still has an active `FieldLink` as target returns `409 FIELD_ORIGIN_CONFLICT`.
- Migration B (`add_lineage_pins` finalize) downgrade is **unsafe** once `DEPRECATED` fields exist: they map to `is_tech=False` on rollback, which violates the Phase 1 "mapped target needs source" invariant. Hold Migration B until the organization is confident the forward direction is stable.
- Lockstep bump of all four packages (`aide-schemas`, `backend`, `aide-sdk`, `aide-crawler`) when `aide-schemas` has a breaking change. No dual-support transitional state.

## 10. Out of Scope (confirmed)

Called out here so a future reader does not mistake their absence for an oversight:

- **Auto-propagation** of source schema changes into new target schemas (with automatic `CastRule` application). Phase 4.
- **Webhook / push alerts** on drift or compat-status flip. Phase 4.
- **Persisted compat history** (audit log of when a link transitioned between statuses). Phase 5+.
- **Lineage graph UI** for compat visualization. Separate frontend track.
- **Binding-level `FieldLink`**. Rationale in §3.3.
- **Gradual migration / dual-support** API accepting both `is_tech` and `origin`. Lockstep bump instead.
- **Scoped compat views** (e.g. `/systems/{id}/compat` aggregated across all links inside one system). Bulk list with `system_id` filter covers the practical need.
- **Rate-limiting / caching** of the compat endpoint. Query is cheap; revisit if monitoring polling becomes aggressive.
